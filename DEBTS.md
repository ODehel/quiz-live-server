# Dettes techniques — quiz-live-server

Source de vérité unique des dettes assumées. Une dette **soldée est supprimée** (git garde l'historique), jamais barrée. Chaque ligne indique, quand il existe, le *pas séparé* qui la solderait. Mis à jour à chaque session, dans le commit de la session.

## questions/

- **Validateur instancié en dur dans la route** (DIP) — `new UuidFormatValidator()` dans le `POST` et le `GET` : deux occurrences. Injection via `QuestionRouteConfiguration` à la troisième (touche `question-route.test`, `server.test` ×2, `index.ts`).
- **Codes d'erreur en littéraux** — `'NOT_FOUND'`, `'INVALID_UUID'`, `'UNKNOWN_FIELDS'`, `'INVALID_BODY'`, `'VALIDATION_ERROR'` dans `question-route.ts` ; aucune constante correspondante dans `error-codes.ts`. `'NOT_FOUND'` est aussi écrit en littéral deux fois dans `theme-route.ts` (depuis le `fix(themes)` du 2026-11-06) : extraction avec la constante, à la prochaine occurrence.
- **Corps du `403` du middleware vide** — `authentication-middleware.ts` répond `403` sans corps (`reply.status(403).send()`), la spec attend `FORBIDDEN` (`error-codes.md`, US-004 CA-33). Relevé le 2026-11-07 à la lecture du code, non sondé en conditions réelles ; `authentication-middleware.test.ts` n'asserte que le statut. Le code `FORBIDDEN` n'existe pas dans `error-codes.ts`. *Pas séparé* : `fix(authentication)`, même gabarit que le `401` (`sendErrorBody`).
- **`choices` requis et typé à la route pour un MCQ seulement, `title` et `correct_answer` typés pour tous les types** — le schéma du `POST` porte `required: ['theme_id', 'title', 'type', 'level', 'time_limit', 'points', 'correct_answer']` : un body sans l'un des sept répond `400 VALIDATION_ERROR` (`Question <champ> is required.`, ou `Question <champ>, <champ> are required.` quand plusieurs manquent ; noms techniques lus dans `missingProperty`, dans l'ordre de `required`, `correct_answer` toujours nommé en dernier). `type` requis à la route double une garde du service (`must be MCQ or SPEED`, qui ne répond plus que pour une valeur invalide). La présence de `correct_answer` n'est gardée qu'à la route (décision #8) : le service appelé sans lui lève un `TypeError`. `choices` est requis par un `if` / `then` du schéma quand `type` est présent et vaut `MCQ` (CA-9) : absent, il répond `400 VALIDATION_ERROR` (`Question choices is required.`), testé sur un body où lui seul manque. Le même `then` type `choices` (`type: 'array'`, `items: { type: 'string' }`) : sur un MCQ, un `choices` qui n'est pas un tableau répond `400 VALIDATION_ERROR` (`Question choices must be an array.`), testé à la route sur `null`, chaîne, nombre, booléen, objet, service non appelé ; un tableau dont une entrée n'est pas une chaîne répond `400 VALIDATION_ERROR` (`Question choices must contain only strings.`), testé sur `[1, 2, 3, 4]` seulement (`['Paris', 'Lyon', 'Nice', null]` : sondé le 2026-10-11, non testé). Le type de `choices` n'est plus gardé qu'à la route : le service appelé sans elle avec un `choices` non-tableau lève un `TypeError` (comme pour la présence de `correct_answer`). Sur un SPEED, la route ne juge pas la forme de `choices` et transmet au service (`must be absent for a SPEED question`), testé sur `[1, 2]`. `title` est typé dans `properties` (`type: 'string'`), donc pour un MCQ comme pour un SPEED : une valeur qui n'est pas une chaîne répond `400 VALIDATION_ERROR` (`Question title must be a string.`), testé sur nombre, `null`, booléen, tableau, objet (MCQ) et sur `42` (SPEED), service non appelé ; le libellé est une invention, la spec n'en prescrit aucun. Le type de `title` n'est gardé qu'à la route : le service appelé sans elle avec un `title` non-chaîne lève un `TypeError`. Une violation de type prime sur un champ manquant et sur un champ inconnu, qui sont tus : testé pour `title` (`points` manquant, `difficulty` inconnu), sondé seulement pour `choices` (2026-10-11). Entre deux champs mal typés, `choices` prime sur `title` (ordre des branches de la garde), testé sur `choices: null` avec `title: 42`. Priorités tracées par la décision #10 ; celle de `choices` sur `title` y est notée sans raison métier. `correct_answer` est typé dans `properties` (`type: 'string'`), pour un MCQ comme pour un SPEED : une valeur qui n'est pas une chaîne répond `400 VALIDATION_ERROR` (`Question correct_answer must be a string.`) au lieu de `500`, testé sur nombre, `null`, booléen, tableau, objet (MCQ) et sur `42` (SPEED), service non appelé ; le libellé est une invention. Le type de `correct_answer` n'est gardé qu'à la route : le service appelé sans elle avec une valeur non-chaîne lève un `TypeError`. Sa branche est la première de la garde : `correct_answer` mal typé prime sur `choices` et sur `title` mal typés, sur un champ manquant et sur un champ inconnu ; sondé le 2026-10-13, testé par aucun test, tracé par aucune décision. Quand `choices` manque avec un autre champ, il est nommé en premier (`Question choices, title are required.`, sonde du 2026-10-09, non committée) : aucun test ne fixe cet ordre. Plusieurs champs requis manquants : tous nommés, testé sur deux couples (`title` + `time_limit`, `theme_id` + `correct_answer`) ; la position de `correct_answer` dans le message n'est assertée par aucun test. Le libellé à plusieurs champs est une invention, la spec n'en prescrit aucun. Quand un champ requis manque **et** qu'un champ inconnu est présent, le manquant prime (décision #9), testé sur une combinaison. Non testé sur le serveur assemblé.
- **`createQuestion` accepte plus large que sa signature** — `CreateQuestionInput` décrit un body valide, mais le service reçoit un body dont seuls les noms de champs sont vérifiés : garde de `type`, `"choices" in input` sur un SPEED. Deux gardes que le type déclare impossibles ; les tests les atteignent par `as unknown as CreateQuestionInput`. *Pas séparé* : `required` et types dans le schéma, ou paramètre typé comme entrée non validée.
- **La garde ne reconnaît que trois mots-clés Ajv** — `type` est trié par `instancePath`, chaque branche exigeant le mot-clé et le chemin sur la même violation (`/choices/<n>` → `must contain only strings`, `/choices` → `must be an array`, `/correct_answer` → `must be a string`, `/title` → `must be a string`, racine `""` → `INVALID_BODY`) ; tout autre chemin lève une exception (`No branch handles the type violation at: …`, donc un `500`) : branche inatteignable tant que chaque champ typé a la sienne, qu'aucun test ne peut donc couvrir, `required` répond `VALIDATION_ERROR` quel que soit le champ, tout le reste est lu comme un champ en trop (`params.additionalProperty`) : une erreur d'un autre mot-clé, ou un `required` sans `missingProperty` (cas non attendu d'Ajv, écarté par le test `!== undefined`), répondrait `Unknown field(s): .`. Les erreurs sont typées à la source par un type local `SchemaViolation`, affirmé (`as`) sur le `any` de Fastify : `tsc` vérifie désormais les lectures, mais le type est une affirmation sur la forme d'Ajv, non vérifiée à l'exécution. *Pas séparé* : une branche par champ typé, à écrire avec le type du champ.
- **`INVALID_BODY` testé sur le seul body `[]`** — `null` et les primitives produisent la même erreur Ajv (sonde du 2026-10-07, non committée) ; aucun test dédié, car aucune mutation ne les distinguerait du tableau.
- **`allErrors` sur une entrée non fiable** — l'Ajv du plugin valide le body jusqu'au bout pour nommer tous les champs inconnus ; la documentation d'Ajv le déconseille face à des entrées non fiables. Risque borné par le rate-limit et la taille maximale du body, non mesuré.
- **Liste des champs connus non figée par les tests** — ajouter un champ quelconque à `properties` ne fait rougir aucun test (mutant survivant assumé : seuls `image_path`, `audio_path`, `difficulty` sont nommés par les CA).
- **Messages d'erreur en dur** — « The requested question was not found. » (→ `NotFoundError(resource)` à la 2ᵉ ressource : quiz, partie) et, depuis le `fix(themes)` du 2026-11-06, « The requested theme was not found. » écrit deux fois en littéral dans `theme-route.ts` (même extraction) ; « The provided ID is not a valid UUID. » dans `sendInvalidUuid` et, depuis le `fix(themes)` du 2026-11-01, en littéral dans `theme-route.ts` (→ `common/` avec `sendErrorBody`, à la 3ᵉ route : extraire maintenant ou à la prochaine occurrence). « An unexpected error occurred. Please try again later. » est écrit en littéral dans `question-route.ts` et, depuis le `fix(themes)` du 2026-11-05 (#36), dans `theme-route.ts` (même extraction).
- **Corps d'erreur écrits en ligne hors de `sendErrorBody`** — `sendErrorBody` et `ErrorBody` vivent dans `common/send-error-body.ts` depuis le `fix(authentication)` du 2026-11-07 (consommateurs : `question-route.ts` et le middleware, pour le `401`). `theme-route.ts` (une douzaine de `reply.status(...).send({ ... })`, dont ceux de son `sendError`) et `token-route.ts` (deux) écrivent encore le corps en ligne. *Pas séparé* : `refactor` route par route, sous les tests existants.
- **`ConflictError` et `ValidationError` en double** (`themes/`, `questions/`, classes identiques) — `NotFoundError` est déjà dans `common/` ; migration des autres erreurs génériques à la 3ᵉ occurrence.
- **`getAll` du repository ne contrôle ni `page` ni `limit`** — `ORDER BY created_at DESC, id DESC LIMIT ? OFFSET ?` avec `(page - 1) * limit` : `limit` et `page` sont appliqués (six tests dont trois sur `page` ; un `LIMIT` ou un `OFFSET` figé est tué). Valeurs limites sondées le 2026-10-17 (SQLite 3.51.3) : `LIMIT -1` renvoie toutes les lignes (sans borne), `LIMIT 0` aucune ; `page` à 0 ou négative donne un `OFFSET` négatif traité comme 0, donc la première page revient sans erreur ; un décalage non entier (`page` 1.5 avec `limit` 1), `NaN` ou `Infinity` lèvent une `SqliteError` (`datatype mismatch`) ; le contrôle de CA-29 / CA-30 est à la route (décision d'Olivier du 2026-10-18 ; CA-29 et CA-30 faits). *Pas séparé* : CA-32 (table vide), puis le reste de la pagination (CA-28 à CA-32). Le service ne contrôle pas non plus `page` ni `limit` (voir la ligne sur le service).
- **Format de `created_at` non contrôlé, récence de l'id non contrôlée** — le tri sur du texte ne suit l'ordre chronologique que si `created_at` est un ISO UTC de largeur fixe (CA-17, `toISOString()`), ce que le repository ne vérifie pas (une date sans millisecondes ou avec décalage casserait le tri sans erreur). Le départage à égalité de date se fait sur `id DESC` : il ne signifie « le plus récent » que si l'id est un UUIDv7, ce que le repository ne vérifie pas non plus (le générateur le garantit, pas le repository). *Pas séparé* : le contrôle des formats se décide avec CA-16 / CA-17.
- **`getAll` du service de liste ne contrôle ni `page` ni `limit`** — `DefaultQuestionService.getAll(page, limit)` renvoie l'enveloppe `{ data, page, limit, total, total_pages }` : deux tests (page 2, `limit` 5, total 12 ; page 1, `limit` 10, total 20, multiple exact), douze mutations tuées par la paire (`floor`, `round`, `floor + 1`, `ceil((total + 1) / limit)`, `total: questions.length`, arguments inversés, `getAll(1, 20)` figé, `getAll(2, 5)` figé, `page`, `limit`, `total` et `total_pages` figés). Le service ne contrôle ni `page` ni `limit` : sondé le 2026-10-17, `Math.ceil(12 / 0)` donne `Infinity`, `Math.ceil(0 / 0)` donne `NaN`, un `limit` négatif donne un nombre négatif de pages ; aucun test, le contrôle de CA-29 / CA-30 est à la route (décision d'Olivier du 2026-10-18 ; CA-29 et CA-30 faits). Le résultat de `count()` du repository est lu par un cast (`as { count: number }`), comme dans `sqlite-theme-repository.ts`. *Pas séparé* : CA-31 et CA-32 au service.
- **Route `GET /api/v1/questions` : `401` non testé** — vingt tests (CA-26 page 2 / `limit` 5, CA-26 page 3 / `limit` 10, CA-28 défauts, CA-29 `limit=200` rejeté, `limit=100` accepté, `limit=101` rejeté, CA-30 : `limit` 0, `A`, `-3`, `1e1`, `007`, `1.5` et `page` 0, `A`, `1e1`, `007`, `1.5`, `-1` rejetés en `400 INVALID_PAGINATION`, corps standard `{ status, error, message }`, service non appelé ; CA-54 corps standard du `500` ; CA-54 log de l'erreur technique). `request.query` contient des chaînes : la garde teste `limit` et `page` avec `isWrittenPaginationNumber` (`common/is-written-pagination-number.ts`, regex `/^[1-9][0-9]*$/` : que des chiffres, premier chiffre non nul : `0`, les négatifs, les décimaux, la notation scientifique, l'hexadécimal, les zéros en tête et la valeur vide sont rejetés), puis `limit > 100` (CA-29) ; la conversion reste `Number(page)` et `Number(limit)`, et le cast `as { page?: number, limit?: number }` laisse au compilateur un type faux. Mutations mesurées le 2026-10-21 : le point toléré dans la regex de `limit` (seul `limit=1.5` tombe), le point toléré dans celle de `page` (seul `page=1.5`), le tiret facultatif dans celle de `page` (seul `page=-1`), la regex de `limit` sans premier chiffre non nul (`limit=0` et `limit=007` tombent). Une valeur vide ou répétée (`limit=1&limit=2`, lue comme un tableau) est rejetée d'après la lecture de la regex, non testée. Le `401` (CA-50) n'est pas testé sur la liste ; le log de l'erreur de `GET /:id` n'est asserté par aucun test. *Pas séparé* : les douze tests CA-30 ont le même corps (à paramétrer) ; CA-50 sur la liste.
- **Décalage `(page - 1) * limit` et défauts de pagination écrits deux fois** — la formule du décalage figure dans `sqlite-theme-repository.ts` et `sqlite-question-repository.ts` (une expression sur deux requêtes SQL distinctes) ; les défauts `page = 1` et `limit = 20` figurent dans `theme-route.ts` et `question-route.ts`. L'enveloppe `Pagination<T>` est construite par `buildPagination` (`common/`) depuis le `refactor(pagination)` du 2026-10-31. Laissés volontairement (choix d'Olivier du 2026-10-31). *Pas séparé* : extraire à la troisième occurrence (US-006 filtrage, liste de quiz).
- **CA-3 non asserté à la route** — la normalisation du titre (trim + collapse) n'est testée qu'au service (CA-003) ; `question-route.test.ts` mocke le service et ne contient ni `trim` ni `normali`. *Pas séparé* : un test de route monté avec le vrai `DefaultQuestionService` (mutation : retirer `normalizeTitle`), montage que ni `question-route.test.ts` ni `server.test.ts` n'ont aujourd'hui.
- **`row.choices!`** dans `rowToQuestion`.
- **`UNIQUE` sur le titre en base** = 2ᵉ source de vérité vis-à-vis de CA-5 (unicité insensible à la casse portée par le service).
- **Test `getByTitle` SPEED champ par champ** (13 `expect`). Cosmétique.
- **Payload SPEED de test dupliqué** → builder `aSpeedQuestion(theme)`. Les fixtures `storedQuestion` et `firstQuestion` de `default-question-service.test.ts` (CA-26) en sont deux copies de plus.
- **`QuestionService` simulé à quatre endroits** (`question-route.test.ts`, `server.test.ts` deux fois, `ws-route.test.ts`) : ajouter `getAll` à l'interface a obligé à modifier les quatre montages. *Pas séparé* : montage commun (fabrique de simulacre) à décider avec le `refactor`.

## authentication/

- **`429` des tokens non re-testé** (`token-route.test.ts:140`, statut seul).
- **Claim `role` du JWT numérique** — le payload porte `role: 0` (`UserRole.ADMIN`) ; la spec (US-003 CA-3) écrit `"admin"` ou `"buzzer"`. `toRoleLabel` (`users/role-label.ts`) existe déjà. `authentication-middleware.ts` et `jwt-decoder.ts` lisent le rôle numérique : émettre le libellé oblige à le reconvertir au décodage. Les tokens déjà émis (durée de vie 3600 s) cesseraient d'être lus de la même façon au déploiement. Constaté le 2026-11-03. Décision d'Olivier (2026-11-03) : le code est à corriger, avec tests unitaires. *Pas séparé* : `fix(authentication)`, un rouge sur le payload émis, un sur le décodage.
- **`UNKNOWN_FIELDS` prime sur un champ manquant sur `POST /api/v1/token`, à l'inverse de la décision #9 (questions)** — choix d'Olivier du 2026-10-30, raison non consignée ; la spec (US-003 CA-6, CA-9, CA-10, CA-12) ne fixe aucun ordre. Sondé le même jour : `{"username":"u","extra":1}` répond `400 UNKNOWN_FIELDS`, `{"username":"u"}` répond le `400` natif de Fastify. Aucun test n'asserte le cas cumulé. Le plugin des tokens a son propre Ajv `allErrors` (même réserve que `questions/`). *Pas séparé* : une décision #N qui dise si les deux routes divergent, puis `test(authentication)`.
- **Tests CA-9 et CA-10 de `token-route.test.ts` : libellés croisés, corps non assertés** — le test « CA-9 » (`username` manquant) envoie `{ username }`, donc un `password` manquant ; le test « CA-10 » (`password` manquant) envoie `{ login }` : les deux manquent **et** un champ est inconnu, il répond désormais `UNKNOWN_FIELDS` (sondé le 2026-10-30) et n'exerce plus le renvoi de l'erreur native. Un `username` manquant seul n'est testé par aucun test. Les deux n'assertent que le statut `400` : le corps est le corps natif de Fastify (`FST_ERR_VALIDATION`), alors que la spec demande `VALIDATION_ERROR` (CA-9, CA-10) ; `INVALID_JSON` (CA-11) n'est pas asserté non plus. Mutant tué par le seul test « CA-9 » : suppression du renvoi de l'erreur native (2026-10-30). *Pas séparé* : `test(authentication)`, puis `fix(authentication)` pour le corps.
- **Test du `UserRepositoryParticipantResolver`** : fake inconditionnel.
- **`JwtValidator` / `JwtDecoder` instanciés deux fois** dans `index.ts`.

## websocket/

- **Remplacement de session silencieux dans les logs** — `ws-route.ts` ferme l'ancienne socket avec le code `4004` (« Session replaced. ») sur deux chemins : un second admin remplace l'ancien, et une nouvelle socket remplace celle du même sujet. ## infrastructure/ & composition

- **`Content-Type: text/plain` non sondé sur `questions/` et `authentication/`** — Fastify parse `text/plain` en chaîne par défaut ; sur les thèmes, `POST` et `PUT` répondaient `400 UNKNOWN_FIELDS` au lieu de `415` (CA-8, CA-26), soldé par `removeContentTypeParser('text/plain')` dans une instance encapsulée de `theme-route.ts` (le `DELETE`, lui, doit continuer à ignorer le `Content-Type`, CA-31a). Les routes `POST /api/v1/questions`, `PUT /api/v1/questions/:id` et `POST /api/v1/token` n'ont pas été sondées avec `text/plain` ; leur schéma Ajv peut répondre autrement. Le même retrait serait à recopier dans chaque plugin de route : à extraire à la 3ᵉ occurrence. *Pas séparé* : sonde, puis `fix(questions)` / `fix(authentication)` si l'écart existe, un rouge par route.
- **Message `Retry-After` et `timeWindow` découplés** dans le rate limit.
- **Signature `rateLimitMiddleware` / `middleware` dupliquée** entre les configurations de routes. *Pas séparé* : `refactor(infrastructure)`.
- **Mots de passe par défaut rejetés par le validateur du seed** — `ProcessEnvironment` donne `admin123` (8 caractères) et `player123` (9) par défaut, et `OwaspPasswordValidator` exige 12 à 72 caractères ASCII : sans variables d'environnement (ou `.env`) à 12 caractères au moins, `npm run seed` échoue avec `Invalid password`, et le hub démarre sur une base vide. L'en-tête de `scripts/smoke-themes.ps1` annonce toujours `admin123` par défaut. Relevé le 2026-11-03 à la lecture du code et par un `401` sur base vide ; confirmé en smoke test le 2026-11-05 : seed lancé sans variables, `401 Invalid credentials` ; avec des mots de passe de 12 caractères au moins, l'authentification passe. *Pas séparé* : décider entre retirer les défauts (échec clair au démarrage) ou les allonger, et aligner l'en-tête du script.
- **Composition `index.ts` non vérifiée à l'exécution** — smoke test (`npm start` + `curl`) jamais fait : `POST`, `GET /:id`, `404`, `400`.
- **Construction de `QuizServer` répétée** dans 7 `beforeEach` (relevé le 2026-11-01).
- **Espions `console.log` jamais restaurés** (`server.test.ts`, CA-2 à CA-4) : ni `mockRestore` dans le fichier, ni `restoreMocks` dans `vitest.config.ts` (relevé le 2026-10-26). Effet sur les tests non mesuré.
