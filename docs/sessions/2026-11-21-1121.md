## Leçons de méthode
- **Rendez-vous par fichiers plutôt que fenêtre de temps** : une attente fixe de 300 ms après la lecture ne garantit pas que le second processus (démarrage `tsx` ~1 s, dispersé) soit dans la fenêtre. Deux rendez-vous par marqueurs (après la lecture de la table vide hors transaction ; dans la transaction, après l'annonce du `BEGIN` de l'autre, plus 200 ms de latence) rendent la course réelle à chaque exécution. Le marqueur `.begun` est écrit avant le `BEGIN`, donc attendre l'autre dans la transaction ne peut pas bloquer l'instance qui tient le verrou.
- Patcher `Statement.prototype` et non une instance : couvre le `BEGIN` / `COMMIT` internes de `better-sqlite3`.
- Lint : un `.mjs` sous `src/` n'est pas dans le `tsconfig` et casse `eslint src` (règles typées) ; `ignores` ciblé plutôt que d'élargir le `tsconfig`.
- Un test d'arrêt doit prouver que le point a bien été atteint (marqueur écrit avant le `SIGKILL`), sinon il passe à vide quand le point n'existe pas (cas du mutant sans transaction pour `commit`).
- Environnement : Linux, root, Node 22 ; Windows (neutralité du test seulement raisonnée : `process.kill(process.pid, 'SIGKILL')`, chemins par `path.join` et `pathToFileURL`) et disque réseau non joués.
