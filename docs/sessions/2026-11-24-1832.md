## Décisions
- **#95** : le seed ignore `MAX_REQUESTS_PER_MINUTE` (voir ci-dessus).
- **Choix de rédaction, pas du CDC, à challenger en revue** :
  1. **Forme** : un nouveau CA-10 dans US-002 (section « Variable que le seed ignore ») plutôt qu'une note datée, parce que CA-8 et CA-9 ont été ajoutés ainsi pour des règles observables ; les notes datées d'US-002 ne servent qu'aux retraits de CA (CA-5). Conséquence : un CA de plus à tester (au moins un test).
  2. **« Comme si elle n'existait pas »** : écrit pour couvrir aussi un seed qui échoue pour une autre cause (mot de passe, `BCRYPT_COST`, base) : le message et le code de cette cause sont inchangés. Le CDC d'Olivier dit « réussit ou échoue exactement comme si elle n'existait pas » ; l'énumération (sorties, code, comptes créés ou non) est de moi.
  3. **`.env`** : le CA-10 dit « dans l'environnement réel ou dans le `.env` » ; c'est une extension naturelle de « quelle que soit sa valeur », non dite par Olivier.
  4. **Valeurs citées** : `abc`, `0`, `2147483648`, blancs seuls, vide ; libellés « Variable que le seed ignore » et « Jamais de message qui nomme `MAX_REQUESTS_PER_MINUTE` » : choix de rédaction.
  5. **Pas d'ajout** à US-003 : « Portée » renvoie à US-002 CA-10 ; aucun CA ajouté ni renuméroté dans US-003.

## Leçons de méthode
- Une règle « la variable n'a aucun effet » se teste par comparaison (même sortie, même code qu'avec la variable absente), pas par un message attendu : le CA-10 est écrit dans ce sens.
- Un fix du hub qui passe par un constructeur partagé (`ProcessEnvironment`) peut changer le seed sans que le CDC du seed le voie : à garder en tête pour la lecture des autres variables.
