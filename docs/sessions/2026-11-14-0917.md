## Choix à challenger
- Emplacement `src/index.test.ts` (inclus par `vitest.config.ts`, à côté de `index.ts`).
- Le message est jugé par `PORT`, `1` et `65535` sur stdout + stderr confondus, pas par le libellé exact (#46 : le libellé est un exemple).
- « N'écoute sur aucun port » est prouvé indirectement : sortie en code `1` avant tout message de démarrage, et rien n'écoute sur 3000. Un `PORT` invalide n'a pas de port à sonder.
- Cinq valeurs invalides seulement (`""` pour #45, `abc`, `8080abc`, `65536`, `0`) : la règle détaillée reste à `read-port.test.ts`.
- Chaque lancement coûte environ 0,5 s ; en échec d'un mutant, 20 s de délai par test (`WAIT_MS`).
- Port libre obtenu puis relâché (course théorique), comme le test de CA-1 de `server.test.ts`.
- Non vérifié ici : le chemin Windows (`taskkill`, `windowsHide`). La CI est sous Ubuntu.

## Leçons de méthode
- Le brief annonçait `npm ci` fait : `node_modules` était absent. Réel avant brief.
- `tsx` lance le programme dans un second processus : tuer seulement le parent laisse un hub sur son port. D'où la mort du groupe de processus.
- Un test de composition ne gagne pas de couverture (enfant non instrumenté) : la preuve est dans les mutants, pas dans le pourcentage.
